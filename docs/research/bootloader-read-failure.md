# Сбой ручного чтения mtd0

> Источник: контекст ручной работы владельца. Причина не установлена. Ниже нет инструкций по ремонту, записи или обходу.

## Наблюдение

При ручном чтении `mtd0` процесс остановился:

- частичный файл: `260096` байт (`0x3F800`);
- ошибка:

```text
libmtd: cannot read 2048 bytes from mtd0
eraseblock 1, offset 129024
error 19: No such device
```

- dmesg:

```text
read data ecc failed at page127 blk1 chip0
```

## Что это значит

Это наблюдение сбоя чтения. Оно **не** доказывает физический дефект NAND. Окончательная причина не установлена.

Возможная гипотеза: в родственном драйвере отображение `page127` может соответствовать `physical page128`. Это остаётся гипотезой, а не доказанным дефектом конкретной версии прошивки или драйвера.

## Чего проект не делает

В коде нет и не должно появляться:

- повторного чтения `mtd0`;
- пропуска сбойной страницы;
- `dd`-обхода;
- отключения ECC;
- `--noecc`;
- дополнения частичного файла `FF`;
- обрезки файла;
- чтения reserved через непроверенные интерфейсы;
- «экспериментального» флага для `mtd0`.

Это осознанное ограничение, а не забытая функция. `mtd0` исключён из `ALLOWED_BACKUP_IDS`, а `validate_backup_ids` возвращает отдельную ошибку.

## Почему нельзя просто повторить

Повторное чтение без анализа:

- может снова дать ошибку;
- может увеличить нагрузку;
- может создать ложное впечатление, что «в этот раз получилось»;
- не решает вопрос ECC и отображения страниц;
- не делает частичный файл полным.

Инструмент не выполняет автоматических повторов. При ошибке статус фиксируется как `failed`, дальнейшее копирование останавливается, а фактическое состояние файлов указывается в `files`.

## Что осталось несохранённым

- Полный `mtd0`.
- BBT/ENV/KEY/DTB/DDR.
- Reserved-области.
- Диапазон между `mtd0` и `mtd1`.

Эти данные нельзя считать покрытыми текущим backup. Вопросы восстановления требуют отдельного исследования и выходят за границы проекта.
