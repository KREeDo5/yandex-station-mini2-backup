# yandex-station-mini2-backup

Экспериментальные инструменты и документация для резервного копирования **Яндекс Станции Мини 2 с часами (YNDX-00020)** по уже настроенному root SSH. Только чтение. Без прошивки и без гарантии восстановления.

> **Весь программный код этого проекта сгенерирован искусственным интеллектом.** Документация также подготовлена с использованием ИИ. Результаты ИИ могут содержать ошибки, небезопасные предположения и неполные проверки. Не считайте код прошедшим независимый аудит безопасности. Перед использованием изучите исходники и оцените риски самостоятельно.

Дополнительно:

- Локальные тесты **не доказывают безопасность реального оборудования**.
- Проверенный вручную опыт владельца **не означает**, что автоматизация из этого репозитория уже проверена на устройстве.
- Успешные mock-тесты **нельзя выдавать** за hardware validation.
- При появлении человеческих правок описание происхождения в `AI_DISCLOSURE.md` нужно актуализировать.

Полное раскрытие: [AI_DISCLOSURE.md](AI_DISCLOSURE.md). Отказ от ответственности: [DISCLAIMER.md](DISCLAIMER.md).

## Статус

- Версия: `0.1.0`.
- Основная поддерживаемая платформа: macOS.
- Linux: planned/unverified.
- Windows: planned; готовых `.bat`/`.ps1` нет.
- Запуск нового инструмента на реальной колонке: **не выполнялся**.
- Аппаратная валидация: **отсутствует**.
- Тесты: локальные unit-тесты на синтетических данных, без доступа к устройству.

## Что это

- Получение страховочных копий доступных MTD-разделов `mtd1`–`mtd6` через `nanddump` по SSH.
- Файловое резервное копирование каталога `/bkupgrade` в tar-поток.
- Проверка целостности локальных файлов по размерам и SHA-256.
- Создание внешней копии с побайтной проверкой.
- Versioned JSON-отчёт с явными ограничениями.

## Чего это не делает

Это **не**:

- полный физический дамп NAND;
- инструмент получения root;
- инструмент прошивки;
- инструмент восстановления;
- гарантия unbrick;
- инструмент обхода secure boot или USB-пароля;
- официальный проект Яндекса.

Результат нельзя называть `full dump`, `raw physical NAND backup` или `recovery-ready backup`.

## Жёсткие ограничения

1. **`mtd0` не читается никогда.** Нет экспериментального флага, нет обхода, нет повторного чтения.
2. Нет записи в NAND, нет `flash_erase`, `nandwrite`, `ubiformat`, `dd`-обхода и изменения ECC.
3. Нет остановки Quasar и других служб.
4. Нет `sync` с обещанием согласованного снимка.
5. Нет перемонтирования или отсоединения UBI.
6. Нет загрузки утилит на колонку.
7. Нет автоматических повторов чтения после ошибки.
8. Нет произвольного `--device /dev/...`: только `mtd1`–`mtd6` из профиля.
9. Нет `StrictHostKeyChecking=no`, `ssh -t`, `shell=True` и парольного SSH.
10. Нет восстановления и нет заявления, что восстановление проверено.

## Что не покрыто

- Физический OOB/spare и полный физический дамп.
- Полный `mtd0`.
- BBT/ENV/KEY/DTB/DDR и другие reserved-области.
- Диапазон между `mtd0` и `mtd1` (его нельзя называть пустым).
- Offline-согласованный снимок UBI.
- Независимое повторное чтение NAND.
- Проверка восстановления.
- Аппаратная валидация этого инструмента.

Подробнее о границах восстановления: [docs/research/recovery-status.md](docs/research/recovery-status.md).

- macOS для команд `check` и `backup`.
- Python 3.11+.
- Системный клиент OpenSSH.
- Уже настроенный root SSH на порт 2222 с ключевой аутентификацией.

## Установка и запуск

Зависимостей нет. Из корня репозитория:

```sh
python3 -m mini2_backup --help
```

На macOS команда `python3` может указывать на Python 3.9. Используйте `python3.12 -m mini2_backup ...` или обёртки `scripts/*.sh`: они сами ищут Python 3.11+.

Или через обёртки:

```sh
scripts/check.sh --help
scripts/backup.sh --help
scripts/verify.sh --help
scripts/copy-external.sh --help
```

Обёртки ищут Python 3.11+ (`python3.13`, `python3.12`, `python3.11`, затем `python3`). Можно задать интерпретатор явно:

```sh
MINI2_PYTHON=/path/to/python3.12 scripts/check.sh --help
```

`pip install .` не требуется. Если вы всё же ставите пакет, появится команда `mini2-backup`, но это не обязательный сценарий.

## Быстрый старт

Все примеры используют заполнители. Не подставляйте чужие значения и не публикуйте свои.

### 1. Диагностика

```sh
scripts/check.sh \
  --host <DEVICE_HOST> \
  --port 2222 \
  --user root \
  --identity <PATH_TO_ROOT_KEY>
```

`check`:

- проверяет macOS, отсутствие запуска внутри SSH, наличие `ssh`, параметры host/port/identity и настроенный `known_hosts`;
- подключается только по ключу, с `StrictHostKeyChecking=yes` и `BatchMode=yes`;
- выполняет фиксированные read-only команды: `id -u`, модель из device tree, `uname`, `/proc/mtd`, sysfs-геометрию MTD, наличие и опции `nanddump`, наличие `tar`;
- не читает конфигурации Quasar, токены, Wi-Fi-пароли, SSH-ключи и не запускает `strings`;
- не заявляет версию прошивки, если её нет надёжного источника. `--firmware-version` сохраняется как `user_provided` и не является доказательством совместимости;
- считает неизвестную/нечитаемую модель hard failure для v0.1. Строка семейства Mini 2 не доказывает артикул YNDX-00020: совпадение `YNDX-00020` фиксируется только как строковое совпадение, а семейство без артикула даёт предупреждение и не отменяет MTD-gate.

Точный профиль разметки и геометрии — обязательный gate. При несовпадении `backup` блокируется. Флага `--force` нет.

Стандартные интерфейсы MTD не отдают смещения разделов. Инструмент не подставляет их: gate проверяет набор устройств, имена, размеры, `erasesize`, `writesize` и `oobsize`. Смещения остаются справочными (`offsets_verified: false`) и не используются для адресации чтения; чтение идёт по `/dev/mtdN`.

### 2. План без подключения

```sh
scripts/backup.sh --dry-run --yes \
  --host <DEVICE_HOST> \
  --port 2222 \
  --user root \
  --identity <PATH_TO_ROOT_KEY> \
  --output-root backups \
  --partitions mtd1,mtd2,mtd3,mtd4,mtd5,mtd6
```

`--dry-run` не подключается к колонке, не запускает `nanddump`/`tar`, не читает разделы и не создаёт каталог результата. Он только печатает план.

### 3. Резервное копирование

```sh
scripts/backup.sh \
  --host <DEVICE_HOST> \
  --port 2222 \
  --user root \
  --identity <PATH_TO_ROOT_KEY> \
  --output-root backups
```

По умолчанию:

1. Показывает план, оценку размера и предупреждения.
2. Требует ввести `yes`.
3. Создаёт новый уникальный каталог `backups/backup-<timestamp>-<random>/`.
4. После подтверждения выполняет read-only preflight и требует прохождения MTD-gate.
5. Читает выбранные разделы `nanddump --bb=padbad --omitoob /dev/mtdN`.
6. Сохраняет каждый образ сначала как `.part`.
7. Переводит `.part` в финальное имя только после exit code 0, точного размера, SHA-256 потока и повторного SHA-256 локального файла.
8. Создаёт `bkupgrade.tar` из `/bkupgrade`.
9. Пишет `report.json` и `checksums.sha256` только для успешно завершённых файлов.

При любой ошибке:

- частичные файлы сохраняются, если они есть; фактическое состояние `.part` и final указано в `files`;
- журнал сохраняется, но ошибки записи/flush/fsync/close журнала не блокируют failed-отчёт и не подменяют первоначальную причину;
- статус фиксируется как `failed`;
- дальнейшее копирование останавливается;
- общий `SUCCESS` не выдаётся;
- при ошибке оркестратора незапущенные артефакты помечаются `skipped`, а попытка сохранить failed-отчёт всё равно выполняется. Если отчёт сохранить невозможно, выводится диагностика и возвращается ненулевой код.

Автоматического возобновления незавершённых чтений в v0.1 нет.

### 4. Проверка локальной копии

```sh
scripts/verify.sh backups/backup-<timestamp>-<random>
```

`verify`:

- не подключается к колонке;
- проверяет schema и пути;
- не допускает выхода путей за каталог бэкапа;
- проверяет размеры и SHA-256 потоково;
- проверяет `kind`, `partition`, `name` и `expected_size` по эталонному профилю; `mtd0`, неизвестные partition и повторы отклоняются;
- показывает фактически проверенный набор разделов;
- сообщает о `.part`;
- проверяет структуру tar без извлечения и без исполнения;
- не делает `tar.extractall`;
- не объявляет восстановление проверенным.

### 5. Внешняя копия

```sh
scripts/copy-external.sh \
  --source backups/backup-<timestamp>-<random> \
  --destination /Volumes/<EXTERNAL_DISK>/mini2-copies
```

`copy-external`:

- работает только с локальными файлами;
- требует явно заданный destination;
- создаёт новый уникальный подкаталог;
- ничего не перезаписывает;
- не следует по symlink за пределы исходного дерева;
- копирует symlink как symlink или явно отказывается;
- сравнивает наборы элементов, типы и цели symlink;
- сравнивает обычные файлы побайтно блоками;
- проверяет пустые каталоги;
- сообщает, что права, даты и xattrs не сравниваются;
- не изменяет исходный бэкап и не пересоздаёт его checksum-файлы;
- пишет отчёт вне сравниваемого дерева;
- требует, чтобы источник оставался неизменным во время операции;
- использует `source_modification_check: inventory_only`, который не обнаруживает все изменения содержимого того же размера;
- не является атомарным снимком: побайтное сравнение выполняется после копирования и не защищает от конкурентных изменений.

На macOS destination по умолчанию должен находиться под `/Volumes`. Это не доказывает физическую независимость: путь `/Volumes` сам по себе ничего не гарантирует. В отчёте указывается `physical_independence: "not_verified"`.

Не извлекайте диск автоматически. После завершения и проверки извлеките носитель безопасным для ОС способом.

## Команды

### `check`

```text
python3 -m mini2_backup check --host HOST [--port 2222] [--user root] \
  --identity KEY [--firmware-version STR] [--json]
```

Exit codes: `0` — все gate-проверки прошли; `2` — локальный preflight или удалённая проверка не прошли.

### `backup`

```text
python3 -m mini2_backup backup --host HOST [--port 2222] [--user root] \
  --identity KEY [--output-root DIR] [--partitions LIST] [--yes] [--dry-run] \
  [--firmware-version STR] [--json]
```

Разрешены только `mtd1`–`mtd6`. `mtd0` отклоняется с отдельным сообщением. Exit codes: `0` — успех; `1` — ошибка передачи/записи/tar; `2` — gate/usage; `130` — прерывание пользователем.

### `verify`

```text
python3 -m mini2_backup verify BACKUP_DIR [--json]
```

Exit codes: `0` — проверка прошла; `1` — ошибка или повреждение.

### `copy-external`

```text
python3 -m mini2_backup copy-external --source DIR --destination DIR \
  [--report FILE] [--allow-non-volume] [--json]
```

Exit codes: `0` — копия создана и проверена; `1` — ошибка или несовпадение; `2` — небезопасные параметры.

## Машиночитаемый вывод

С `--json` команды `check`, `backup`, `verify` и `copy-external` пишут в `stdout` только один JSON-документ. Для `backup` и `copy-external` план, прогресс, предупреждения и приглашение подтверждения направляются в `stderr`. Ошибки в JSON-режиме также выводятся одним JSON-документом в `stdout`, а не смешиваются с текстом.

## Формат результата

```text
backups/backup-YYYYmmdd-HHMMSS-xxxxxx/
├── images/
│   ├── mtd1.tpl.bin
│   ├── mtd2.boot.bin
│   ├── mtd3.system.bin
│   ├── mtd4.nv.bin
│   ├── mtd5.bkupgrade.bin
│   └── mtd6.recovery.bin
├── bkupgrade.tar
├── checksums.sha256
├── report.json
└── backup.log
```

- `report.json` — versioned schema `1.1`, без приватных ключей и секретов. Схема `1.0` поддерживается только как legacy с предупреждением об ограниченной проверке.
- `checksums.sha256` — только успешно завершённые файлы; не включает сам себя и `report.json`.
- `.part` — незавершённый файл; остаётся при ошибке.
- `status: skipped` — артефакт не начинали после более ранней ошибки; это не успех.
- `bytes_received` и `bytes_written` разделены; `stderr_tail` хранит последние байты, `stderr_truncated` отмечает усечение.
- `files` фиксирует фактическое состояние `.part` и final по отдельности. Возможны только `.part`, оба файла или только final. Final не считается проверенным, если `files.final.sha256_verified` не `true`.
- Права на файлы образов: `0600`.

Подробнее: [docs/backup-format.md](docs/backup-format.md).

## Ограничения и риски

- `nanddump --bb=padbad --omitoob` даёт логический поток через драйвер. Плохие блоки заменяются `FF` с сохранением длины. Это не физический OOB.
- ECC остаётся по умолчанию. `--noecc` и `--oob` не применяются.
- Разные версии `nanddump` могут иметь разный синтаксис. Поддержка опций проверяется до чтения.
- UBI остаётся подключённым. Даже после остановки Quasar Dropbear может писать журнал. Offline-согласованность не подтверждена.
- Проверка SHA-256 не доказывает правильность исходного чтения NAND.
- Внешняя копия не равна независимому повторному чтению.
- Наличие бэкапа не означает наличие рабочего восстановления.
- Архив `/bkupgrade` может содержать секреты, токены, ключи и персональные данные. Не публикуйте его.

Подробнее: [docs/limitations.md](docs/limitations.md), [docs/troubleshooting.md](docs/troubleshooting.md).

## mtd0: почему его нет

В ручном опыте чтение `mtd0` остановилось:

- частичный файл: `260096` байт (`0x3F800`);
- ошибка: `libmtd: cannot read 2048 bytes from mtd0`, eraseblock 1, offset 129024, `error 19: No such device`;
- dmesg: `read data ecc failed at page127 blk1 chip0`.

Это не доказательство физического дефекта; окончательная причина не установлена. Гипотеза о сопоставлении page127 с physical page128 в родственном драйвере остаётся гипотезой. Поэтому в коде нет:

- повторного чтения `mtd0`;
- пропуска сбойной страницы;
- `dd`-обхода;
- отключения ECC;
- дополнения частичного файла `FF`;
- чтения reserved через непроверенные интерфейсы.

Подробнее: [docs/research/bootloader-read-failure.md](docs/research/bootloader-read-failure.md).

## Тесты

Локальные тесты не требуют устройства и не открывают SSH:

```sh
python3.12 -m unittest discover -s tests -t .
```

Флаг `-t .` обязателен: тесты используют относительные импорты внутри пакета `tests`.

Тесты покрывают парсинг `/proc/mtd`, профиль и mismatch, запрет `mtd0`, параметры SSH, отказ при неподтверждённом окружении, потоковую передачу, ошибки и `.part`, отсутствие перезаписи, SHA-256, `verify` с повреждением и path traversal, безопасный просмотр tar, symlink, внешнюю копию и отсутствие реальных SSH-подключений. Отдельно покрыты семантическая проверка `kind`/`partition`/`name`/`expected_size`, legacy-схема, JSON-вывод, ошибки журнала, контролируемый `OSError` в оркестраторе и прерывания на этапах hardlink, directory fsync, удаления `.part` и fallback.

CI, если присутствует, запускает только локальные тесты без IP и секретов.

## Приватность и публикация

`.gitignore` исключает локальные бэкапы, образы, `.part`, tar, отчёты, приватные ключи, `.env` и загруженные OTA. Пример отчёта в `examples/` — синтетический.

Не публикуйте:

- дампы и OTA;
- токены, ключи и пароли;
- логи владельца;
- полные отчёты с путями и именами устройства без редактирования.

См. [SECURITY.md](SECURITY.md) и [CONTRIBUTING.md](CONTRIBUTING.md).

## Источники, реестр и доказательства

История исследования восстановлена по семи журналам контекста. Это не новая проверка доступности сайтов и не гарантия, что журналы сохранили каждую открытую страницу. Временные ссылки на сами журналы и подписанные URL не публикуются.

- [docs/research/sources.md](docs/research/sources.md) — реестр источников: что изучали, для какого вывода, известная ветка/tag/commit, способ изучения и ограничения применимости.
- [docs/research/evidence-map.md](docs/research/evidence-map.md) — карта выводов, оснований и уровней подтверждения.

Краткие направления для самостоятельного изучения:

- https://hackalice.me/devices/station-mini2/
- https://hackalice.me/start/root/
- https://hackalice.me/start/ssh/
- https://hackalice.me/start/recovery/
- https://github.com/Marker284/yandex-station-extended

Реестр прямо помечает `not recorded`, если commit не сохранился; текущий HEAD репозитория задним числом не подставляется. Ссылки не подтверждают, что данный инструмент поддержан авторами тех проектов, и не переносят поведение Mini 1/Lite на Mini 2. Необработанные журналы, дампы и OTA не публикуются: в журналах встречался индивидуальный endpoint ID.

Внешние источники в этом репозитории не копировались. При проверке внешних материалов используйте только чтение, указывайте точные URL и не приписывайте источнику неподтверждённые утверждения.
